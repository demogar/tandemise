# P14 plan: GitHub issues in and out

> For agentic workers: REQUIRED SUB-SKILL: superpowers:subagent-driven-development (or executing-plans). Steps use checkboxes.

**Goal:** per-repository opt-in that turns open labelled GitHub issues into draft missions (queued when the issue lists its Done-when criteria, "Needs refinement" otherwise), follows upstream edits and closes, and reports back on the issue (queued, stalled, done with the criteria table) idempotently, closing it only when asked and every criterion was verified.

**Spec:** `docs/superpowers/specs/2026-09-26-p14-issues-design.md`. Branch `feat/p14-github-issues`, base `feat/p13-skills-library` (#28).

**Architecture**
- Pure rules in `@tandemise/domain` (`entities/issue.ts`): settings defaults and validation, GitHub slug from a remote, `parseIssueCriteria`, goal/title, comment bodies and markers, write-back decisions, words. Ports `IssueRepositoryPort` (SQLite) and `IssueTrackerPort` (`gh`).
- `GhIssueTracker` in `@tandemise/integration-github` (`issues.ts`) over the injected `CommandExecutor`, reusing the `gh` error words; bound by the daemon.
- `IssueService` in application: settings, overview, check (poll), write-back, `tick()` for the scheduler (background, one in flight per repository).
- `MissionService.create` origin gains `issueLinkId` (stored on the mission, criteria recorded as from the issue).

**Tech stack:** TypeScript (ESM), better-sqlite3, React 18 + React Query, zod.

**Global constraints:** `npm run ci` green; boundaries (no `child_process` in core; renderer `import type` only); design tokens only; migration 019 additive; comments say why; Conventional Commits.

## Rulings made while planning

- The poll runs `gh` in the repository's checkout folder so `gh` picks up the right host configuration, but always passes `--repo` explicitly.
- The fake `gh` finds its state next to its own script, because the daemon passes only an allow-listed environment to child processes.

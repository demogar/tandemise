# P16 Reach me when it matters: Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (or executing-plans). Steps use checkbox (`- [ ]`) syntax.

**Goal:** One native notification per new Inbox item that is for me, never a flood, never twice, with per-kind switches, quiet hours and a test button; clicking opens the decision.

**Architecture:**
- Pure diff `planNotifications` in `@tandemise/domain` (items, state, preferences, minute of day, suppress → notice | null, state).
- `NotificationService` in `@tandemise/application`: Inbox → items (`itemsFromInbox`), diff, state and preferences in the daemon's `settings.json` (no migration).
- Daemon routes: `GET|PUT /v1/notifications/preferences`, `POST /v1/notifications/take`.
- Desktop main process `Notifier`: polls `take` every 5 s whatever the window state, shows Electron `Notification`, click → show window + route over IPC; test notification; recorder and debug hook behind `TANDEMISE_NOTIFY_RECORD`.
- Renderer: Settings → Notifications section; `useNotificationOpen` in the project shell.

**Tech stack:** TypeScript, zod, Electron 33 `Notification`, React 18 + React Query.

**Spec:** [2026-09-26-p16-notify-design.md](../specs/2026-09-26-p16-notify-design.md)

## Rulings made while planning

1. The diff and its state live in the daemon; the main process only reports "looking at the Inbox" and shows what comes back.
2. `take` computes and records in one synchronous call, so two polls can never announce the same id.
3. The test hook is an env var on the desktop (`TANDEMISE_NOTIFY_RECORD`), not a daemon route: what is asserted is what the main process actually showed.
4. The "focused" signal can be overridden by the hook, because a window driven over CDP may not have OS focus.

# P10: The owner's desk — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Home answers at a glance what needs me, what is moving, how much of "done" is verified, what it cost against my limits and what is stuck, each number opening the view behind it; a status report is rendered from stored facts, byte-identical for the same facts.

**Architecture:**
- Domain: `entities/status-report.ts` — `StatusReportFacts`, `renderStatusReport(facts)` (pure, the fixed template), `statusReportHeadline`, `REPORT_HOLDER_PRESET`; `monthBannerText(status)` and `wipBannerText(counts)` words.
- Persistence: `MissionRepository.list` leaves out the report holder (workflow preset `status-reports`). No migration.
- Application: `DeskService` (token DESK_SERVICE, `services.desk`): `metrics(ws)`, `banners(ws)`, `reportFacts(ws)`, `writeStatusReport(ws, caller)`. Projections: `HomeView.metrics/banners`, `MissionSummary.criteria`. `LimitService.alerts` uses the month banner words. Artifact reader lists a report's versions.
- Daemon: `POST /v1/workspaces/:id/status-report`.
- Desktop: Home desk cards + banners + "Status report" button; `/inbox/stalled`; `/missions/backlog`; `/artifacts/:id`; criteria chip on mission rows.

**Tech stack:** TypeScript (ESM), better-sqlite3, zod, React 18 + React Query, raw CDP for acceptance.

**Spec:** `docs/superpowers/specs/2026-09-26-p10-desk-design.md` (binding, including Rulings).

## Global Constraints

- `npm run ci` green; boundaries and design tokens included.
- No migration (`StatusReport` is already an artifact type, migration 012).
- The report is a pure function of facts; time only from the injected Clock, and only in the front matter.
- Renderer uses `import type` only; existing classes and tokens only; at most one primary button per view.
- Comments explain why; Conventional Commits.

## Rulings made while planning

1. The renderer lives in the domain (pure, no zod); the application validates the rendered file through the existing `ARTIFACT_PARSER` port, so a report that would not parse is never stored.
2. The desk card "Needs you" is computed in the window from the same Inbox read as the badge (for me, minus checks, minus stalled rows); `metrics.needsYou` is the project-wide count used by the report.
3. Mission-row criteria reuse `GateService.trace`, the same read the feed's checklist uses.
4. The desk counts "needs you" from rows (cards, person steps, refinements, silent runs) rather than by building the Inbox, so Home still names each card once per read (the handoff check's approval-cache rule).
5. A release that writes nothing passes a gate that reads only QA facts, so the acceptance suite uses a "P10 desk" workflow whose release gate also needs the ReleaseCandidate.

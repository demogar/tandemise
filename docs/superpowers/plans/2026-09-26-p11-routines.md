# P11: Routines — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a routine adds a ready, queued mission (or writes the status report) on a simple schedule, deterministically from the injected Clock, and can never get past the readiness gate, the WIP limit or the monthly hard limit.

**Architecture:**
- Domain: `entities/routine.ts` — `Routine`, `RoutineSchedule`, `RoutineRun`, pure `firstSlotAfter`, `dueSlots`, `decideRoutineRun`, `scheduleLabel`, `nextRunLabel`, `outcomeLabel`, `routineMissionTitle`, `routineGoal`, starter `ROUTINE_TEMPLATES` (mirrored in the renderer). `Mission.routineId`, `MissionDraft.routineId`. `RoutineRepositoryPort`.
- Persistence: migration 016 (`routines`, `routine_runs`, `missions.routine_id`); `SqliteRoutineRepository`; mission repository reads/writes `routine_id`.
- Application: `RoutineService` (token ROUTINE_SERVICE, `services.routines`): `list`, `create`, `update`, `remove`, `runNow`, `tick`. Scheduler dep `fireRoutines` runs before the backlog pull. `MissionService.create(caller, request, origin?)` takes `{ routineId }`.
- Shared: `adjustableClock(offsetMs)` (a Clock plus `advance`).
- Daemon: `TANDEMISE_CLOCK_OFFSET_MS` → config `clockOffsetMs`; routine routes; `POST /v1/test/clock` only with the knob.
- Desktop: Missions → Routines tab (`screens/missions/Routines.tsx`, `RoutineDialog.tsx`), mission header "From routine: …", `/missions/routines` route.

**Tech stack:** TypeScript (ESM), better-sqlite3, zod, React 18 + React Query, raw CDP for acceptance.

**Spec:** `docs/superpowers/specs/2026-09-26-p11-routines-design.md` (binding, including Rulings).

## Global Constraints

- `npm run ci` green; boundaries and design tokens included.

- Time only from the injected Clock; schedule maths are pure functions; application code never reads `Date.now()`.
- Renderer uses `import type` only; existing classes and tokens only; at most one primary button per view.

## Rulings made while planning

1. Routine missions are created through `MissionService.create` (not the repository), so the creation note, the Done-when ledger, the queue and the wake-up are the same code as "Add to backlog".
2. The next run is claimed (moved forward) in the same synchronous step that decides a run, before the async mission creation, so re-entrant ticks and Run now can never fire one slot twice.
3. The Routines query key lives under `['missions', …]`, so the existing `missions` invalidation refreshes it; no new projection topic.
4. Labels ("Next: Mon 09:00") are computed by the daemon from its Clock, so a shifted test clock and the window always agree.

# P5: Done-when ledger — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every Done-when line becomes a numbered criterion the spec must cover and QA must verify by id; the daemon traces and measures it, and the feed shows it.

**Architecture:**
- Domain: `MissionCriterion` entity, `MissionCriteriaRepositoryPort`, and pure trace/validation rules in `packages/domain/src/entities/criteria.ts` (reused by gates, harvest and the view; P6 builds on them).
- Persistence: migration 011 `mission_criteria`, `SqliteMissionCriteriaRepository`.
- Artifacts: `covers` on ProductSpec criteria, `criterionId` on QAReport results; templates updated.
- Application: harvester validates and records the ledger; `GateService.factsFor` adds criteria facts via `GateFactBuilder.withCriteria`; presets read them; the context compiler prints the ledger; `CriteriaService.list` projects the view.
- Daemon: `GET /v1/missions/:id/criteria`. Desktop: "Done when" section in the feed, relabelled New mission field.

**Tech stack:** TypeScript ESM, zod, better-sqlite3, React 18. Checks are `scratch/*.mjs` against `dist/`.

**Spec:** `docs/superpowers/specs/2026-09-26-p5-done-when-design.md` (binding, including Rulings).

## Global Constraints

- `npm run ci` green at the end; `check:boundaries` and `check:design` included.
- One additive migration (011). Released migrations untouched.
- No new approval kinds. No LLM output decides progression: every new outcome is a gate fact or a harvest refusal.

interface MissionCriteriaRepositoryPort {
  listActive(missionId): readonly MissionCriterion[];

  addUserCriteria(missionId, statements): readonly MissionCriterion[];

}
function traceCriteria(criteria, qa: { results; recordedAt } | null): CriteriaTrace

## Rulings made while planning

See the spec's Rulings (1–11). In addition:
- The criteria service is a separate application service (`services.criteria`) so P6 can add verdict and add-criterion methods beside `list` without touching projections.
- `GateService` and `ArtifactHarvester` take the criteria repository as an optional trailing constructor argument so hand-built harnesses keep compiling; the application module always passes it.

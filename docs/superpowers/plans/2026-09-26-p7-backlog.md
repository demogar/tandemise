# P7: Backlog, priority and a WIP limit — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A ranked backlog of queued drafts; the daemon plans the next ready one, in order, whenever fewer than N missions are in progress.

**Architecture:**
- Domain: `entities/backlog.ts` — priorities, `compareBacklog` (total order), `WIP_PULL_GATE`, `wipFacts`, `isInProgress`, `choosePulls`, `moveInBacklog`, `describeWip`. `Mission` gains `priority`, `rank`, `queuedAt`; `Workspace` gains `maxActiveMissions`. Event `mission.pulled`.
- Persistence: migration 013; mission and workspace repositories read and write the new columns.
- Evaluation: three facts in `GATE_FACT_VOCABULARY`.
- Application: `BacklogService` (view, update, pull) using `ReadinessService.evaluate(id).ready` and `PlanningService.begin`; the scheduler calls `pull` at the top of each pass and dispatches missions in backlog order; `MissionService.create` stores priority/queued and ranks last; `MissionService.cancel` abandons planning; `PlanningService` discards a plan for a mission that left PLANNING.
- Daemon: `GET /v1/workspaces/:id/backlog`, `PATCH /v1/missions/:id`, `maxActiveMissions` on the workspace PATCH.
- Desktop: Missions "Backlog" tab, NewMission priority + "Add to backlog", timeline row for `mission.pulled`.

**Tech stack:** TypeScript (ESM), better-sqlite3, zod, React 18 + React Query, raw CDP for acceptance.

**Spec:** `docs/superpowers/specs/2026-09-26-p7-backlog-design.md` (binding, including Rulings).

## Global Constraints

- `npm run ci` green; boundaries and design tokens included.
- One additive migration (013). Released migrations and 011/012 untouched.
- Readiness only through `ReadinessService.evaluate(id).ready`. The pull is decided by a gate over counts and a total order, never by an agent.

## Rulings made while planning

- The pull runs inside the scheduler pass (not a timer of its own), before dispatch, so a slot freed and a mission pulled are seen by the same pass's reconciliation.
- `BacklogService` is resolved lazily by the scheduler (it depends on planning, which the mission service also composes) to avoid a construction cycle.
- The Backlog query key sits under `missions`, so every mission invalidation (including a pull) refreshes it.

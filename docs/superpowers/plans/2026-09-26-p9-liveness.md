# P9: Nothing waits silently — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every mission that cannot move gets exactly one Inbox item saying what it needs; a quiet agent is reported before its wall-time budget is gone, and the person stops and retries it or keeps waiting.

**Architecture:**
- Domain: `entities/liveness.ts` — `LIVENESS_RULES` (the spec's table, ids L1–L18 and T1–T15), `classifyLiveness(input)` → `{ kind, rule, reason, action }`, `taskLiveness`, watchdog thresholds `watchThresholds(quietMs, budgetMs)`, `watchLevel`, `quietFor` words, `livenessFacts`. `Run.lastEventAt`, `Run.watchSnoozedUntil`; `RunRepositoryPort.markActivity/snooze`.
- Persistence: migration 015 (`runs.last_event_at`, `runs.watch_snoozed_until`); run repository columns and the two writes.
- Application: `LivenessService` (token LIVENESS_SERVICE, `services.liveness`): `classify(mission)`, `stalled(ws)`, `silentRuns(ws)`, `watchOf(task, run)`, `snooze(runId)`, `watch()` (scheduler hook: one note and one invalidation when a run turns quiet or silent), `facts(missionId)`. `PlanningService.isPlanning(id)`. The executor stamps `last_event_at` per agent event. `MissionService.retryTask` accepts `stopRun`. Projections: `InboxView.stalled/silentRuns`, `TaskView.watch`.
- Daemon: `TANDEMISE_QUIET_MS` → `ApplicationModuleOptions.quietAfterMs`; `POST /v1/runs/:id/snooze`; `stopRun` on retry.
- Desktop: Inbox rows `StalledRow` and `QuietRow` (in `screens/Inbox.tsx` and Home), `lib/inbox.ts` item kinds `stalled` and `quiet`, drawer "Last activity … · Quiet", Home blocked cards deduplicated, missions topic refreshes the Inbox.

**Tech stack:** TypeScript (ESM), better-sqlite3, zod, React 18 + React Query, raw CDP for acceptance.

**Spec:** `docs/superpowers/specs/2026-09-26-p9-liveness-design.md` (binding, including Rulings).

## Rulings made while planning

- The rule lives in the domain as one pure function over a small input, so the spec table, the service and the check are the same thing; the service only gathers rows.
- `LivenessService` reads the planner and refinement state through closures resolved per call, since planning is composed after projections and depends on them.
- The watchdog's note and invalidation are in-memory "said once" keys (run, level, snooze): losing them on a restart repeats one note at most.

## 1. `packages/api-contract/src/requests.ts` — request schemas

Every request is a `zod` object with an exported `z.infer` type, validated at the daemon edge. A shared helper handles the P0 "on-behalf-of" rule once and is spread into any request that records work for someone else:

- `const onBehalfOf = z.string().min(1).optional();` (line 12)
- Spread into `createMissionRequest` (line 88), `decideApprovalRequest` (line 109), `completeTaskRequest` (line 154), `giveFeedbackRequest` (line 311), `startRoundRequest` (line 321), `claimTaskRequest`/`dismissFeedbackRequest` (lines 159, 325).

Notable request shapes:

- `createMissionRequest` (line 72) — the richest object: `workspaceId`, `repositoryId`, `goal`, `title`, `constraints`, `successCriteria`, `autonomy`, `workflowPreset`, `workflowInputs`, `baseBranch`, `planNow`, `onBehalfOf`, `staffing` (a `roleStaffingPatchRequest`). This is the canonical example of "add optional fields to an existing request."
- `completeTaskRequest` (line 151) — `{ result: string trim 1..20_000, note?: 2_000, onBehalfOf }`. This is the closest existing analogue to a hand-back: a person brings back `result`, which `mission-service.completeTask` writes as the artifact the step declared.
- `addMemberRequest` (line 175) — `z.discriminatedUnion('kind', [...])`, the pattern for a new request type that forks on a discriminator.
- `giveFeedbackRequest` (line 307) — `{ text 1..4_000, artifactId?, onBehalfOf }`. Its `feedback` table already has an `attachments` column (see §5).
- `startRoundRequest` (line 316) — `{ feedbackIds 1..50, downstream: 'redo'|'keep'|'none', redoTaskIds?, onBehalfOf }`.

**How to add a field or a new request type:**

1. **New field on an existing request** (e.g. `uploads` on `completeTaskRequest`): add a `z.array(...).optional()` entry to the object, and the type is regenerated by `z.infer`. Because the renderer `DaemonClient` imports the inferred type, the field flows to the client automatically. Follow the optional-nullable style already used (`z.string().nullable().optional()` in `updateWorkspaceRequest`, line 31).
2. **New request type** (a hand-back): declare `export const handBackRequest = z.object({...})` + `export type HandBackRequest = z.infer<...>`. Use `onBehalfOf` for the recorded-by rule and `z.discriminatedUnion('kind', ...)` if the payload forks (as `addMemberRequest` does). Then register it in `routes.ts` and add a `DaemonClient` method (§3, §4).

## 2. `packages/api-contract/src/views.ts` — view shapes

Views are read models; the renderer never reads SQLite (header comment, lines 1–15). Relevant shapes:

- `ArtifactView extends ArtifactManifest` (line 30) adds `author`, `responsible`, `recordedByRef` (`ActorRef`s).
- `MissionArtifactView extends ArtifactView` (line 42) adds `version` (1-based along the `supersedes` chain) and `supersededBy: string | null` (line 46).
- `ArtifactReadView` (line 61) carries `manifest: MissionArtifactView`, `body`, `appendixWords`, `split`, `openRequest`, `withdrawnAt`, `round: number | null` (line 83), `versions` (each with `artifactId/version/round/createdAt`, line 88), `changes: readonly FeedChange[]` (line 92), `canRequestChanges` (line 94). Note `round` (line 107 in `FeedbackView`).
- `ArtifactHandoff` (imported from domain) appears on `FeedCard.handoff` (line 197) — already exposing `headline/points/needs/changed/links`.
- `FeedCard` (line 174) already carries `superseded` (line 205), `supersededByTaskKey` (line 207), `round` (line 221), `openFeedback` (line 227), `changed` (line 229). So P3 snapshot/supersede UI has the signals it needs without new view fields, except where an upload needs its own card surface.
- `TaskView` (line 269) has `round` (line 293) and `outputArtifacts: readonly ArtifactView[]`.

The view contract is additive: the `RuntimeView.settingsSchema?` comment (lines 415–424) documents the convention that a field added to a view is **optional** (`?`), because a fresh renderer may talk to an older daemon. Any P3 view field must follow that "absent, not empty" rule.

## 3. `apps/daemon/src/routes.ts` — route registration

`buildRouter(services: TandemiseServices): Router` (line 25). Handlers are thin: parse → delegate → return. Two local helpers do the work:

- `query<T>(ctx, schema)` (line 39) parses query strings with a zod schema.
- `required(ctx, name)` (line 45) fetches a mandatory query param.

Registration patterns:

- `r.get('/v1/home', ...)`, `r.post('/v1/workspaces', async (ctx) => services.workspaces.create(ctx.caller, await ctx.body(createWorkspaceRequest)))` (lines 52–59).
- Missions: `r.get('/v1/missions', ...)`, `r.post('/v1/missions', async (ctx) => { const mission = await services.missions.create(...); return services.projections.missionDetail(mission.id); })` (lines 78–89). Note the POST returns the full `MissionDetail`.
- `r.post('/v1/missions/:id/plan' | '/start' | '/pause' | '/resume' | '/cancel', ...)` (lines 91–97).
- `r.post('/v1/tasks/:id/retry' | '/skip' | '/complete' | '/claim', ...)` (lines 106–111). `complete` uses `completeTaskRequest`.
- Feedback/rounds: `r.post('/v1/tasks/:id/feedback' | '/rounds', ...)`, `r.get('/v1/tasks/:id/feedback')`, `r.post('/v1/feedback/:id/dismiss', ...)` (lines 113–119).
- Artifacts: `r.get('/v1/artifacts')` (search) and `r.get('/v1/artifacts/:id')` (read) (lines 155–158).

**Where a hand-back/upload route slots in:** an upload or hand-back is a task-scoped action, so it belongs beside the task/feedback block (after line 111), e.g. `r.post('/v1/tasks/:id/complete', ...)` already exists as the hand-back analogue; a distinct `r.post('/v1/tasks/:id/upload', ...)` or `r.post('/v1/tasks/:id/handback', ...)` would follow the same shape: `async (ctx) => services.missions.…(ctx.caller, asId(ctx.params.id!), await ctx.body(handBackRequest))`. Artifact-scoped routes (`/v1/artifacts/...`) would slot near line 158. A new schema must be imported in the top import block (lines 2–11).

## 4. `apps/desktop/src/renderer/src/lib/daemon.ts` — `DaemonClient`

Transport helpers:

- `async #request<T>(method, path, body?, query?)` (line 106): builds `new URL('/v1'+path, connection.url)`, sets query params, sends `authorization: Bearer`, `API_VERSION_HEADER`, JSON `content-type` + `body`, 30s timeout, unwraps errors via `toDaemonError` (line 470).
- `#get<T>(path, query?)` (line 143) wraps `#request('GET', ...)`.

Example methods (all just `this.#request`/`this.#get` one-liners):

- `createMission(body: CreateMissionRequest): Promise<MissionDetail>` → `this.#request('POST', '/missions', body)` (line 190).
- `completeTask(id, body: CompleteTaskRequest): Promise<TaskView>` → `this.#request('POST', `/tasks/${id}/complete`, body)` (line 209).
- `giveFeedback(taskId, body: GiveFeedbackRequest): Promise<FeedbackGivenView>` → `this.#request('POST', `/tasks/${taskId}/feedback`, body)` (line 220).
- `missionArtifacts(id, query)` → `this.#get('/missions/${id}/artifacts', query)` (line 203); `artifact(id)` → `this.#get('/artifacts/${id}')` (line 286).

**To add a client method:** import the new request type from `@tandemise/api-contract` in the type-import block (lines 1–54), then add a method in the matching section, e.g.:

```ts
handBack(id: string, body: HandBackRequest): Promise<TaskView> {
  return this.#request('POST', `/tasks/${id}/handback`, body);
}
```

Uploads that carry binary are the one place `#request`'s JSON-only body is a mismatch; a multipart/form-data variant (or a body that is a `Blob`/`FormData`) would be a new helper alongside `#request`.

## 5. `packages/persistence` — artifact repo, migrations, P3 fit

### Artifact repository (`repositories/artifact-repository.ts`)

Implements `ArtifactRepositoryPort` (declared in `packages/domain/src/ports/repositories.ts` lines 112–133). Key methods:

- `create(manifest: ArtifactManifest): ArtifactManifest` (line 217) — inserts the `artifacts` row (`toRow`), writes `sourceRefs` into `artifact_links`, and if `manifest.supersedes !== null` calls `#markSuperseded` to set the back-pointer (`superseded_by = :by`) in the same transaction.
- `get`, `listByMission(missionId, type?)`, `listByTask`, `latest(missionId, type)`, `search`, `listRecent`, `markSuperseded(id, by)`, `withdraw(ids, at)` (lines 224–263).

`sourceRefs` (`ExternalRef[]`) are stored normalized in `artifact_links` (`artifact_id, ordinal, kind, value, label`) — see `#writeLinks` (line 266) and `#linksFor` (line 277). `ExternalRef.kind` is `'git.commit' | 'git.branch' | 'github.pr' | 'github.issue' | 'url' | 'file'` (`domain/entities/artifact.ts` line 43). `ArtifactManifest` (line 49) already carries `sourceRefs`, `supersedes`, `recordedBy`, `handoff`, `round`, `withdrawnAt`; `ArtifactWriteRequest` (line 99) is the store's input shape. `ArtifactStorePort.write(request)` (`domain/ports/artifact-store.ts` line 10) returns a manifest; bodies live on the filesystem, content-addressed by `sha256`.

`supersedes`/`superseded_by` are declared in migration 001 (`001_initial.ts` lines 331–333), with the denormalized back-pointer indexed at line 337.

### Migrations (`migrations/index.ts`)

`MIGRATIONS: readonly Migration[]` (line 32) — append-only. `SCHEMA_VERSION` derives from `max(version)`. `migrate()` (line 68) runs pending migrations each in its own transaction with its ledger row; `assertOrdered` (line 151) enforces gapless versions. A new P3 migration is `migration011` exported from `migrations/011_*.ts`, imported and appended to the array.

The `Migration` shape (`migrations/types.ts` line 23): `{ version, name, up: string, transform? }`. `up` is raw SQL; `transform` gets the raw `SqliteHandle`. The 009 docblock (`009_artifact_handoff.ts` lines 1–30) is the cautionary reference for touching `artifacts`: it has a generated `handoff_text` column and an FTS5 external-content index; a rebuild must name columns and never `INSERT ... SELECT *`.

### Does P3 need a new table?

- **`feedback.attachments`**: already present. `migrations/010_feedback_rounds.ts` line 25 creates `attachments TEXT NOT NULL DEFAULT '[]'`. `SqliteFeedbackRepository` round-trips it as `toJson`/`parseJson<readonly FeedbackAttachment[]>` (lines 33, 48). `FeedbackAttachment` is currently `Readonly<Record<string, unknown>>`, explicitly documented "Reserved for P3 (uploads, hand-backs); always empty in P2" (`domain/entities/feedback.ts` line 13). So P3 feedback attachments need **no schema change** — only a concrete `FeedbackAttachment` type and (optionally) a `giveFeedbackRequest` field, since today `feedback-rounds.ts` line 128 always writes `attachments: []`.

- **Stored plan JSON**: there is **no persistent plan JSON column**. The planner writes a transient `plan.json` into the agent worktree (`planning-service.ts` lines 471–472, under `ARTIFACT_OUT_DIR`), which is parsed by `parsePlanResponse` and **materialized into `mission_tasks` rows** (`mission_tasks` table, 001 lines 83–115). The plan is then stored twice: as structured task rows (reconstructed by `projection-service.missionDetail` via `asPlannedTasks(tasks)`, lines 357–360, and never stored as a JSON blob) and as a rendered `MissionPlan` markdown **artifact** (`renderPlanDocument`, `materialize.ts` line 123; written in `planning-service.#storePlanDocument` line 573). `decideApprovalRequest.editedPlan` is `z.unknown()` (requests.ts line 104) — an edited plan passes through the decide path but is not a separate persisted JSON.

**Verdict:** uploads (attachments) and hand-backs (new request/route reusing `ArtifactWriteRequest` + `ArtifactManifest.sourceRefs`/`supersedes`) can be built on the existing `artifacts` + `artifact_links` + `feedback` tables and the existing `ArtifactStorePort.write`/`SqliteArtifactRepository.create` path. Snapshots are already modeled as superseded artifact versions. The only likely new migration is for any upload-specific metadata (e.g. an `uploads` table or a `feedback`/`artifacts` column), which would be `migration011`, appended to `MIGRATIONS`.

## Key wiring summary for the implementation plan

| Concern | Existing surface to reuse |
|---|---|
| New request field | extend existing `z.object` in `requests.ts` (e.g. `completeTaskRequest` line 151, `giveFeedbackRequest` line 307) |
| New request type | `export const handBackRequest = z.object({...})` + `z.infer` type; use `onBehalfOf` (line 12) |
| Route | `routes.ts` task/feedback block (lines 106–119) — `async (ctx) => services.missions.../ctx.body(...)` |
| Client | `DaemonClient` one-line `#request`/`#get` method (e.g. `completeTask` line 209) |
| Artifact creation | `ArtifactStorePort.write(ArtifactWriteRequest)` → `SqliteArtifactRepository.create(ArtifactManifest)` (auto-sets `superseded_by`) |
| External pointers | `ArtifactManifest.sourceRefs: ExternalRef[]` → `artifact_links` table |
| Snapshot/supersede | `supersedes`/`superseded_by` columns + `markSuperseded`/`withdraw`; surfaced as `MissionArtifactView.version`/`supersededBy` |
| Upload attachments | `feedback.attachments` JSON column (010, line 25) — ready, no table needed |
| Plan persistence | materialized `mission_tasks` rows + `MissionPlan` markdown artifact — no JSON table |
